Part 1 · WordPress vs Astro + Payload0 – 4 min

WordPress vs Astro + Payload: what changes

WordPress today
  • The content model (CPTs, ACF groups) is rows in wp_postmeta, built in wp-admin. No diff, no review, no rollback.
  • Renaming an ACF field: edit it in wp-admin on every environment, then grep the templates for the old key.
  • Plugins for SEO, caching, images, forms. Each runs PHP on every request and needs updating.
  • First contentful paint measured in seconds: theme JS, plugin CSS, uncached PHP render.
Astro + Payload
  • The content model is a TypeScript file in git. It goes through a pull request like any other code.
  • Payload generates TypeScript types from the collections; Astro imports them. Rename a field and the build lists the broken templates.
  • Astro renders HTML on the server from Payload's REST API. No database connection, no client JS unless you add it.
  • Claude Code reads the collections, the types and CLAUDE.md, and writes the boilerplate under review.

Do not bash WordPress. Half the room is proud of their WP work and rightly so. The framing is: WP made a trade that was correct in 2010. Content model in a database so non-devs could build it. We are a dev shop, and for us that trade now costs more than it gives.

Pick one real Webee example for the nine-second line if you have one. A real client name lands harder than a made-up number.

Say the shape of the next 19 minutes: everything you know has a name on the new stack. We go through the names, Payload first, then Astro, then one slide that sorts them into same, different and new.

Part 1 · why teams make the move0 – 4 min

Why teams move to Astro + Payload

1

Performance by default

Astro emits static HTML; JavaScript ships only for components marked as islands. No caching layer, image plugin or minifier to configure.

2

A much smaller attack surface

No third-party PHP executing per request, no wp-admin login endpoint on the public site, and the frontend holds no database credentials.

3

The content model is code

Collections and fields are TypeScript in git: reviewed in PRs, versioned, identical on every environment. No schema drift between staging and production.

4

Typed from field to template

payload generate:types emits one Project type; Astro templates import it. A renamed field fails the build with the list of affected files.

5

Open source, self-hosted, one language

Payload and Astro are MIT licensed. No per-seat fees or premium plugin renewals, TypeScript on both sides, deployable to any Node or static host.

6

npm packages, not plugins

Astro components, npm packages, and a schema an AI tool can read because it is code. The frontend is decoupled: a redesign does not touch the content.

Editors keep an admin UI, rich text, media library, drafts and roles. Developers stop maintaining plugin updates.

This is the "why" slide. Keep it to ninety seconds and say the honest version: WordPress is still the right answer for a site a non-developer must build and run alone, and for a client who wants a theme marketplace. We are a development shop with clients who pay for performance, security and change requests. For that work, the six reasons on this slide are why the stack changed.

Reason 3 is the one that connects to everything after it. The rest of the talk is what it looks like when the content model is code. Reasons 1 and 2 are the ones clients feel. Reason 5 is the one management asked about.

If someone objects that WordPress can be headless too, agree: it can, and that is the half-step many teams took first. The difference is that the model still lives in a database and the frontend still reads untyped JSON. Payload closes that gap.

Part 1 · the whole talk in three ideas0 – 4 min

Three ideas the rest of the talk builds on

Idea 1

The content model lives in code

A collection file is the CPT registration and the ACF group in one TypeScript object. Payload generates the admin UI and the REST API from it.

Idea 2

The frontend only consumes the REST API

Part 1 · Payload in WordPress vocabulary7 – 13 min

One collection file generates three things

1

An admin panel

Every field becomes a form control at /admin. Change the file, restart, the form changes. No screen to click through.

2

A REST API

/api/services exists the moment the collection is registered. Filtering, sorting and pagination are query params.

3

TypeScript types

pnpm generate:types writes a Service type the frontend imports. Rename a field and the build finds every use.

+

Nothing until it is registered

Add the collection to the array in payload.config.ts or it does not exist. The most common step-1 failure.

Live demo: add { name: 'tagline', type: 'text' } to Services.ts, restart the CMS, check /admin, then GET /api/services.

This is the live round trip and the most important five minutes of the talk. Do it by hand, no Claude, slowly.

Predict before reveal: before you refresh /admin, ask "what will be different?" Before you refresh /api/services, ask "will tagline be in the JSON already, or only after I fill it in?" (It is there as null immediately for existing docs. That surprises people and teaches that the shape comes from the file, not the data.)

Then add one line to ServiceCard.astro to render the tagline and refresh the site. That is the whole architecture demonstrated end to end.

Part 1 · Astro in WordPress vocabulary13 – 19 min

The PHP at the top of the template is now the frontmatter

WordPress archive-service.php 
<?php get_header();
$q = new WP_Query([
  'post_type' => 'service',
  'orderby'   => 'menu_order',
]); ?>

<h1>What we do</h1>
<div class="grid">
<?php while ($q->have_posts()): $q->the_post();
  get_template_part('template-parts/content', 'service');
endwhile; ?>
</div>

<?php get_footer();
Astro apps/web/src/pages/index.astro 
---
import Base from '@/layouts/Base.astro'
import ServiceCard from '@/components/ServiceCard.astro'
import { getDocs } from '@/lib/payload'

const { docs: services } = await getDocs('services', {
  sort: 'order',
})
---
<Base title="Services">
  <h1>What we do</h1>
  <div class="grid">
    {services.map((service) => (
      <ServiceCard service={service} />
    ))}
  </div>
</Base>

Map it line by line, this is the slide WP devs relax on. The dashes fence off the frontmatter: that is the PHP block at the top of the template. WP_Query becomes getDocs. get_header and get_footer become the Base layout wrapping the page. get_template_part becomes a component with a prop. The while loop becomes a map.

One difference worth naming: the frontmatter runs on the server at request time, and never in the browser. Nothing in it ships to the client.

Explain-back, 90 seconds: turn to the person next to you and tell them how a Service gets from the collection file to a card on this page. Pick two people to say it out loud. You are listening for the words file, admin, JSON, fetch, component.

Part 1 · the query, and the one idea with no WP name13 – 19 min

Querying: where in the query string, depth for relationships

WordPress a relationship field gives you IDs 
$ids = get_field('services');   // [3, 1]
foreach ($ids as $id) {
  $post = get_post($id);          // one query each
  echo $post->post_title;
}

Each related post is a separate get_post() call and a separate query.

Payload GET /api/projects?depth=1 
{
  "title": "Harbour Ferries Booking",
  "services": [
    { "id": 1, "slug": "web-development",
      "title": "Web Development", … }
  ]
}
// depth=0 → "services": [1]
// depth=1 → populated one level, as above

The generated type is number | Service: an id at depth 0, a document at depth 1. Guard with typeof s === 'object'.

Depth is the concept most likely to confuse them in the hands-on, because it has no WordPress word. Spend a real minute here.

The union type number | Service is the payoff of idea 1. The type is honest: at depth 0 you get an id, at depth 1 you get the document. The compiler makes you handle both. In PHP you would find out in production.

Check: "If I set depth=2 on a project, what comes back inside each service?" Answer: whatever the service relates to, populated. Most will get it; the ones who do not will meet it in card A and now have a name for it.

Part 1 · similar, different, new13 – 19 min

Same concepts, different architecture, three new terms

Maps one to one
  • CPT → collection
  • ACF field group → fields
  • Options page → global
  • Archive / single template → pages/…/index.astro, [slug].astro
  • Template part → component
  • save_post → beforeChange
Different
  • The content model is a file in git, not rows in a database
  • Types flow from the CMS into the frontend
  • The frontend has no database and no credentials
  • No template hierarchy: the folder is the URL
  • npm packages in package.json instead of plugins
New, no WordPress name
  • depth: how far relationships are populated
  • Generated types, and the number | Service guard
  • Global vs collection: one document vs a list
  • SSR vs SSG: per request, or built once

This is the summary of part 1 and the slide to leave on screen if someone asks "so what actually changes?". Three columns, read the headings only, then one line each.

Left column: everything you have built in WordPress has a place to go. Middle: the five things that feel strange for a week and then feel obvious. Right: the four words that have no WordPress equivalent; when someone gets stuck this afternoon, it is usually one of these.

Check: ask "which column does a slug go in?" Trick question, it is in the first column twice: post_name maps to a field you define, and the post type name maps to the collection slug. If someone says that, part 1 landed.

Part 2 · how you will work19 – 24 min

Working rules, enforced by the gate

1

Plan mode first

Shift+Tab before anything that touches more than one file. You see the plan, then the diff.

2

Read every diff before you accept

Which files changed, and did I ask for all of them? What breaks without this? Could I do it by hand tomorrow?

3

Ticket-style prompts

Paste the step from the brief, acceptance criteria included. Underspecified prompts produce underspecified diffs.

4

Commit only when the gate is green

pnpm verify N, then the exact message with its (step N) tag. The commit hooks refuse a tagged commit while the step is red.

5

Ask for the explanation

Anything you could not reproduce by hand tomorrow, ask "why" until you could.

!

Never bypass the hooks

Never edit .claude/hooks, scripts/verify.mjs or .env, never add --no-verify. If Claude proposes that as the fix, the fix is wrong.

These are the Claude Code standards they have already seen, with one addition: rule 4 is now enforced by a script, not by culture. Say that plainly. pnpm verify N runs the acceptance criteria for steps 0 to N, in order, against your running servers and your git log, and stops at the first red. A commit tagged (step N) is refused by the hooks until N is green. Removing the tag to get around it just leaves verify red, and you will see it.

The framing that works with juniors: Claude is faster than you and knows more syntax than you, and it is also wrong in ways that look confident. That is exactly what a junior on your team is. You would not merge a junior's PR unread. Same rule.

Rule 6: Claude will occasionally propose editing the hook or the verify script as the fix, calmly and confidently. Naming it in advance means someone in the room will catch it and enjoy catching it.
